# Contribution workflow

- Make future changes on a branch and submit a pull request. Do not push changes directly to main.
- Routing PR artifacts must show only successfully completed routes. Include a routed snapshot for each declared AM3352 benchmark sample and inspect every image before submitting. Never commit or attach iteration-zero, intermediate, failed, or unrouted snapshots as PR artifacts; keep diagnostic captures local. Snapshot exporters must verify solver success and complete connectivity before writing artifacts.
- Explicit exception: the OrangeCrab byte-zero, byte-one and two-byte reproductions may track clearly labeled failed baselines in `repros/orangecrab-byte0/board.snap.svg`, `repros/orangecrab-byte1/board.snap.svg` and `repros/orangecrab-data-bytes/board.snap.svg`, so the stacked fix can replace the same file with validated completed output. This exception does not relax completed-route acceptance checks or permit failed AM3352 gallery images.
- Explicit exception: the user-requested STMP157 fourth-byte reproduction may track its clearly labeled failed solver state in `tests/__snapshots__/stmp157-byte3.snap.svg`. It may show unaccepted candidate copper, which must not be described as completed routing. The stacked fix replaces that same file only after all eight requested signals and DRC pass. AM3352 completed-output requirements remain unchanged.
- Explicit exception: the user-requested A64 fourth-byte reproduction may track `tests/__snapshots__/a64-preloaded-byte3.snap.svg` showing only the supplied, previously completed 24 routes and a clearly labeled failure for the eight new signals. The stacked fix replaces it only after all 32 connections, DRC and supplied-copper preservation pass. No unaccepted candidate copper or failed AM3352 images may be published.
- Explicit exception: the user-requested A13 CPU-side DDR byte reproduction may track its clearly labeled failed baseline in `tests/__snapshots__/a13-cpu-byte0-pcb.snap.svg`. Show native pads and no unaccepted candidate copper. The stacked fix replaces it only after all eight requested signals, connectivity and DRC pass. AM3352 completed-output requirements remain unchanged.
- Explicit exception: the user-requested H616 second-byte reproduction may track `tests/__snapshots__/h616-preloaded-byte1-pcb.snap.svg` showing only the eight supplied, previously completed routes and a clearly labeled failure for the eight new signals. The stacked fix replaces it only after all 16 connections, DRC and supplied-copper preservation pass. No unaccepted candidate copper or failed AM3352 images may be published.
- Explicit exception: the user-requested A13 second CPU-byte reproduction may track `tests/__snapshots__/a13-preloaded-byte1-pcb.snap.svg` showing only the eight supplied, previously completed routes and a clearly labeled failure for the eight new signals. The stacked fix replaces it only after all 16 connections, DRC and supplied-copper preservation pass. No unaccepted candidate copper or failed AM3352 images may be published.
- Never merge a PR without reporting its effect on the benchmark in the PR description. Green CI alone does not satisfy this requirement. Keep the analysis current with the final production-code revision.
- For solver, routing, dependency, fixture, or benchmark changes, run `./benchmark.sh` on pinned base and head revisions with the same fixtures, harness, budgets, runtime, and comparable resource allocation. Report per-case and aggregate solved counts, connectivity, DRC, per-bus total copper length skew, pair skew/coupling, runtime, and regressions. Include the commands, revision IDs, environment, and result provenance so the comparison can be reproduced. Do not count a routing-only pass as a length-matching pass.
- Report failures, timeouts, incomplete runs, and missing comparisons explicitly. Separate fresh solves from retained-output revalidation; neither saved routes nor search-equivalence tests establish fresh solve performance. Do not claim a speedup from incomparable timings. A missing final-revision base/head comparison leaves benchmark validation incomplete and must be completed and reported before merge.
- Documentation-only PRs must still include a benchmark-effect statement explaining why benchmark behavior is unchanged; they need no fresh solver run unless they change executable behavior or benchmark inputs.
- Every PR must freshly solve and validate all 11 AM3352 benchmark samples in the Blacksmith workflow. Keep the `AM3352 benchmark (11/11)` acceptance check green before merge. Use a 3,600-second per-solver/sample budget and allow slow samples to finish; saved-route revalidation never satisfies this check. The paired base/head measurements and raw reports are retained as CI artifacts and the comparison is published in the workflow summary.
- Keep fixed FanoutSolver outputs immutable and retain their provenance. Matching measurements include both fixed fanouts and the new interconnect.
